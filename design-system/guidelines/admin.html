Quizzer Design System · Artifact 5 of 5

Admin console

Desktop-first. The admin surface uses the same tokens but a different surface strategy: ambient B (flat wash) and glass recipe B (solid-leaning), because these views hold long tables, line-numbered errors and six-figure numbers where translucency is a liability. Glass is reserved for the commit bar and dialogs.

■
Two irreversible acts, both surfaced in the component. Committing an import writes rows to the bank — nothing is written until commit, and every variant of the commit bar says so. Locking a quiz permanently retires its questions: they can never be drawn again. Both use Batch 2b's destructive-confirm — type-to-confirm for the lock.

Sample marks scheme throughout, matching Batch 4: +3 correct, −1 wrong, up to +0.5 speed bonus per question, so a 20-question quiz is out of 60.

Pick sheet — Batch 5

ComponentABCRecommended

Open questions

  • When is the draw made? Rendered as: drawn at build time, visible to the admin, re-drawable until lock. If instead questions are drawn per student at open time, draw-preview and composition-report both change meaning entirely.
  • Does locking retire questions immediately or at close? Assumed at lock. The bank's "Retired" badge depends on it.
  • Can a locked quiz be edited or unlocked? Assumed no, ever. That is what makes the type-to-confirm justified.
  • CSV schema. Invented for these components: stem, section, difficulty, topic, type, option_a–d, correct_option, answer, tolerance, explanation, image, passage_id, passage_text. Send the real header row and I'll align every error message to it.
  • Passage set size. Assumed 4–5 children, enforced as a validation error outside that range.
  • Speed bonus formula. The decay curve is drawn as linear from the end of the grace window to zero at the question limit. If it's exponential, only the polyline changes.
  • Seat cap semantics. Assumed seats are consumed on join and never released, so a full room stays full.
  • Report visibility. Assumed every admin sees every student's results, and students never see another student's breakdown. The promote dialog says so.
  • Live monitoring and void. Entirely speculative — no product decision exists. If monitoring is not wanted, the quiz-card-schedule "Monitor" action disappears too.
  • Recurrence and locking. Assumed recurrence generates drafts and never auto-locks, so a human always approves the draw.
