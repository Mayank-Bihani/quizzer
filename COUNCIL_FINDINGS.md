# Quizzer — LLM Council Design Audit

> **Historical record:** findings and resolutions below describe the pre-2026-09-09 design.
> Current V1 timing, batch submission, scoring, schema and API rules live in [[PRD]],
> [[QUIZZING]], [[DATA_MODEL]], [[CONTRACTS]] and [[API]]. Conflicting historical rules are
> superseded by [[V1_CHANGES]]; audit entries are preserved, not silently rewritten.

> **Scope:** every module, data model, contract, and request/response shape — MODULES.md,
> CONTRACTS.md, API.md, AUTH.md, BANK.md, QUIZZING.md, SCHEDULER.md, TELEGRAM.md,
> `migrations/0001_init.sql`, `src/core/contracts.ts`, `src/core/api.ts`, cross-checked against
> PRD.md, PLAN.md, JOURNEYS.md, AUDIT.md, wrangler.toml, package.json.
> **Method:** 5 independent AI advisors (Contrarian, First-Principles, Expansionist, Outsider,
> Executor) each read every file and produced 10–18 file-grounded findings; a second round had
> all 5 peer-review the anonymized full set to find convergence, blind spots, and overstated
> claims; findings below are deduplicated across both rounds. IDs cite the advisor finding(s)
> merged into that row.
> **Status:** audit complete, no fixes applied yet — this document is the punch list.
> **Date:** 2026-09-05

---

## How to read this

- **Severity** is the council's post-peer-review judgment, not any single advisor's.
- **Suggested fix** is the council's proposal — not a decision. Same split as AUDIT.md §11's
  "Options considered" column.
- **Resolution** is empty on purpose. That's yours to fill in — accept, reject, defer, or pick
  a different fix — the same way AUDIT.md §11's "Decision" column records the project owner's
  call, not the auditor's.
- The **Rejected** table at the end holds findings at least one advisor raised but peer review
  concluded aren't real defects against the current spec; kept for transparency, not for a
  Resolution call.

## Critical

| # | Finding | Evidence | Suggested fix | Resolution |
|---|---|---|---|---|
| 1 | **Telegram "claim row, then send" cannot be written.** `message_id` and `sent_at` are `NOT NULL`, but neither is known until *after* `sendMessage` succeeds. Found independently by all 5 advisors — the strongest single signal in the whole audit. There's also no status/failure column, so a permanently-failed send is indistinguishable from a delivered one, and `MODULES.md`'s "alert on a TG-3 that failed to send" has nothing to query. | `migrations/0001_init.sql:224-233`, `TELEGRAM.md:188-199`, `CONTRACTS.md:146-148` | Make `message_id`/`sent_at` nullable; add `status TEXT CHECK (status IN ('pending','sent','failed'))` + `error TEXT`. Insert the claim row with `status='pending'` before calling the Bot API; UPDATE to `sent`/`failed` after. The unique constraint on `(quiz_id, kind)` still does the idempotency work at insert time. | **Accepted** — apply as proposed. |
| 2 | **A drafted, unlocked quiz is indistinguishable from a locked, ready one.** `QuizStatus` has no `draft`/`locked` state — both sit at `'scheduled'`. The cron open pass matches `lobby_opens_at <= now AND status = 'scheduled'` and will seed seats and open a room over a quiz whose questions were never claimed. | `migrations/0001_init.sql:65-66,58,69`, `QUIZZING.md:73`, `SCHEDULER.md:91` | Add a real `'draft'` status (or a `locked_at` column) and include it in the open-pass predicate's exclusion. `POST /:id/lock`'s 409 ("already locked") then has a column to check. | **Accepted** — apply as proposed. |
| 3 | **The first admin action as specified cannot execute.** `CreateQuizDraftRequest` supplies only `title`/`scheduledAt`/`SelectionFilters`, but `quizzes` requires `lobby_opens_at`, `ends_at`, `room_code`, `time_per_q_sec`, `window_sec`, `grace_sec`, `marks_correct`, `marks_wrong`, `max_speed_bonus` as `NOT NULL` with no DEFAULT — API.md itself defers all scoring params to the later `PATCH`. `INSERT` throws on the very first `POST /api/admin/quizzes`. | `src/core/api.ts:188-191` vs `migrations/0001_init.sql:62-76`; `API.md:116-120` | Resolve alongside #2: either give the scoring columns sane defaults usable pre-lock, or don't write a `quizzes` row until enough is known (draft state lives elsewhere, or the row is written with defaults and `PATCH`-refined before lock). | **Accepted** — apply as proposed, coupled to #2. |
| 4 | **`claimUnused` cannot express whole-passage-group atomicity.** The function takes only question ids; `passages.used_in_quiz_id` has no writer anywhere. D1 `batch()` is atomic against errors, not isolation — a conditional `UPDATE … WHERE used_in_quiz_id IS NULL` matching zero rows is a *success*, so two admins drawing the same RC set can each win part of it with no rollback, permanently splitting a passage group. A short/partial claim also has no release path, so retry-after-redraw burns questions forever, and cancelling a quiz (AUDIT §11 #15) burns its claimed questions with no way to return them to the pool. Widest convergence of the whole audit (5 findings, 4 advisors). | `src/core/contracts.ts:71`; `migrations/0001_init.sql:100,130`; `PLAN.md:474-481`; `BANK.md:152-156,183-184` | Extend `claimUnused` to derive/claim the passage ids alongside question ids in one call; define explicit all-or-nothing semantics (verify claimed count == requested count; if not, release the partial claim before returning the short result). Add a `release(questionIds)` call used by both the redraw-retry path and quiz cancellation. | **Partially accepted** — concurrent admins never happen in practice, so the race/all-or-nothing/auto-release machinery is unnecessary. Just extend `claimUnused` to also claim/mark `passages.used_in_quiz_id` alongside its questions (single-admin correctness bug, independent of concurrency). No `release()` call, no auto-undo-on-short. |
| 5 | **`quizzes` has no `question_count`/`difficulty_mix` column.** `reshuffle`'s "redraw with the same stored parameters," the window-length derivation (`count × time_per_q_sec + slack`), and `QuizAnnouncePayload.questionCount` all need this and it exists only on `quiz_templates`. | `migrations/0001_init.sql:56-83` vs `:42-43`; `src/core/api.ts:200-201`; `src/core/contracts.ts:155` | Add `question_count INTEGER NOT NULL` and `difficulty_mix TEXT` (JSON) to `quizzes`, populated at draft creation from `SelectionFilters`. | **Accepted** — apply as proposed. |
| 6 | **Join at T−5m starts the quiz clock before the window opens.** `JoinQuizResponse` unconditionally returns question 1 and writes `participants.started_at = served_at(1)`. Nothing gates this on `status = 'running'` — the room opens at T−5m (`status='open'`) but the window opens at `scheduled_at`. A student joining early has their clock running for five minutes before the quiz officially starts, and `startQuiz`'s `open→running` transition has no consumer at all — it's dead code as specified. | `src/core/api.ts:247-248`; `migrations/0001_init.sql:173`; `SCHEDULER.md:91-92`; `PRD.md:131` (ROOM-1) | `/join` should return lobby state (seat confirmed, no question) while `status='open'`; only serve question 1 — and start the clock — once `status='running'`, via the same lazy-predicate pattern `openRoom`/`closeQuiz` already use. | **Accepted, model changed** — this is a self-paced quiz: the room stays open for a **join window** (e.g. T to T+30min), and each student's own fixed duration (`window_sec`) starts from *their own* join moment, not a shared clock. `ends_at` becomes "join window closes," not "quiz cutoff" — a late joiner still gets the full duration. This reshapes #10 and #17 too (see there); `startQuiz`'s `open→running` transition is dropped in favor of per-student timing. |
| 7 | **`closeQuiz` triggered from a results route is a ~120-way concurrent stampede with no lock.** At `ends_at`, ~120 clients hit `/status`/`/leaderboard`/`/review` in the same second; if cron hasn't landed, every request reads `board_computed_at IS NULL` and runs a full rank-and-close concurrently — D1 has no `SELECT … FOR UPDATE` or interactive transaction to serialize this. | `QUIZZING.md:169-177`; `CONTRACTS.md:118-126`; `migrations/0001_init.sql:80-82` | Claim-first, same pattern as #1: `UPDATE quizzes SET board_computed_at = ? WHERE board_computed_at IS NULL RETURNING id` — only the winner ranks and warms the cache; every other concurrent request just re-reads the result. | **Accepted** — write `closeQuiz`'s guard as this atomic UPDATE...RETURNING from the start (same amount of code as a check-then-write, zero marginal cost since nothing is built yet). Cron is the primary trigger; this only matters if cron is late and the lazy backup path fires from more than one concurrent student request. |
| 8 | **Guards "mounted per route group" cannot express the one role split that exists.** `POST /api/admin/users/:id/role` is superadmin-only but shares the `/api/admin/*` prefix with every admin-level route. Mount the prefix with `requireRole('admin')` and any admin can self-promote to superadmin; mount it `requireRole('superadmin')` and no admin can create a quiz. | `AUTH.md:79,93-95`; `API.md:49-50,185` | Split into `/api/admin/*` (admin) and a `/api/admin/superadmin/*` or `/api/superadmin/*` sub-prefix (superadmin), or document an explicit route→guard table and stop claiming guards are group-level only. | **Accepted** — apply as proposed. |
| 9 | **`materializeTemplates`'s stated idempotency key doesn't exist.** "Idempotent on `(template_id, scheduled_at)`" is asserted twice; `quizzes` has only a plain, non-unique index on `template_id`. Two overlapping hourly cron ticks produce duplicate quiz rows and each calls `claimUnused` for a different question set against the same occurrence. | `SCHEDULER.md:112,137`; `migrations/0001_init.sql:86` | Add `UNIQUE (template_id, scheduled_at)` to `quizzes` (nullable `template_id` elsewhere is fine — SQLite treats NULLs as distinct in a unique index). | **Accepted** — apply as proposed. |
| 10 | **`window_sec`/`ends_at`/question-count are three representations of one fact, freely desyncable via `PATCH`.** The window is simultaneously "auto-derived" (QUIZ-10 resolution) and admin-settable (`UpdateQuizParamsRequest`); nothing recomputes `ends_at`/`lobby_opens_at` when `scheduledAt`/`windowSec`/`timePerQSec` change independently. Related: no CHECK stops `grace_sec >= time_per_q_sec`, which divides-by-zero the speed-bonus formula into a `NOT NULL` column, failing every `/answer` insert for the whole quiz. | `migrations/0001_init.sql:62-64,71-76`; `QUIZZING.md:80-81,254-255`; `src/core/api.ts:208-218` | Write down the derivation formula once (`ends_at = scheduled_at + window_sec`); recompute both timestamps on any `PATCH` that touches their inputs; reject after `status` leaves `'scheduled'`. Add app-layer validation: `grace_sec < time_per_q_sec`, `marks_wrong <= 0`. | **Accepted, model changed** — per #6, `ends_at` is now "join window closes," not a shared quiz cutoff. Each student's own deadline = their `started_at` + `window_sec`. Validation guards (`grace_sec < time_per_q_sec`, `marks_wrong <= 0`) apply as proposed regardless of the model change. |
| 11 | **`GET /api/images/:key` auth status is undefined and contradicts BANK's own route-group rule.** Every other BANK route lists `403` in API.md; this one lists only `404`. But BANK.md states BANK's whole route group requires `requireRole('admin')` with no per-route exception — yet students must load question images mid-run. One reading 403s every student on every image; the other serves unreleased-question images to anyone who guesses a key. | `API.md:69`; `BANK.md:131,136-137` | Explicitly carve this route out of the admin group: `requireAuth()` only (any signed-in user), scoped so the key is only fetchable once its question has been served or reviewed. Document this exception in BANK.md §5 next to the route. | **Accepted, then reconsidered** — `requireAuth()` only, **no per-question scoping**. The scoping was walked back after Sprint 2's spec packet (`todos/sprint 2/`) surfaced that enforcing it means BANK reading QUIZZING-owned tables (`quiz_questions`, `participants`) to check a student's progress — a real violation of "BANK never reads QUIZZING's tables," to prevent a threat that isn't one: these are illustrative images, not answers, and guessing another question's key gets nothing worth the effort. Same call as #25/#44 — don't defend against a threat this deployment doesn't have. |

## Summary — resolved 2026-09-05 (project owner)

All 44 findings have a **Resolution**. Tally: **32 accepted** (7 with a scope change from what
the council originally suggested), **1 partially accepted**, **1 deferred**, **11 rejected**.

The most consequential re-scoping happened during this pass, not during the original audit:
this is a small, single-admin, trusted-group app, not a large multi-tenant product — so most
of the council's "harden against concurrent admins / adversarial uploads / audit trails /
pagination at scale" findings (#12 partly, #18, #19, #23, #24, #25, #26, #32, #43, #44) were
rejected or deferred as disproportionate to the actual deployment. #4 (`claimUnused`/passage
atomicity) was accepted only in its non-concurrent form — passages need correct bookkeeping
regardless of scale, but the race-condition machinery (auto-release, all-or-nothing claims)
was rejected since concurrent admin actions don't happen here. #16 (re-grading) resolved to
"no feature needed" — manual DB correction already covers the rare case at this scale.

The one finding that changed the actual product design, not just an implementation detail, is
**#6**: this is a self-paced quiz. Students join within a window, and each student's own timer
starts from *their* join moment, not a shared clock — `ends_at` now means "join window closes,"
not "quiz cutoff." This reshapes #10 (window/scoring derivation) and #17 (status timestamps)
as noted in their rows, and should be the first thing reflected across QUIZZING.md, SCHEDULER.md,
and the schema during the bulk-edit pass.

Genuine correctness/reliability fixes that survived regardless of scale: #1 (Telegram
idempotency), #2/#3 (draft vs. locked quiz state), #7 (closeQuiz race — free either way), #14
(idempotent join), #21 (CPU budget — confirmed real on the free plan), #27/#28/#30 (contract
type bugs), #31/#39 (passage import would crash as specified), #34/#35 (leaderboard shape,
answer retry) — these aren't scale-dependent, they're bugs that would surface on day one with
even a single admin and a handful of students.
